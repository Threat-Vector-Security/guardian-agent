# Guardian 2 documentation audit

Archive note: this records the findings before the documentation cleanup. Current instructions are in the [documentation home](../README.md); unresolved application behavior is tracked in [known issues](../KNOWN-ISSUES.md).

Date: 6 September 2026. Reviewed revision: `b7d553bc`.

## Result and scope

The documentation still mixes the original general-purpose assistant with the current security workspace. This is material guidance drift: users can follow incorrect installation instructions, while contributors can be directed into retired runtime paths or assume security controls apply to Guardian 2 when they only describe the old application.

Inventory: 255 tracked files under `docs/`, including 233 Markdown files. The Markdown inventory contains 51 design documents, 46 plans, 42 proposals, 27 test results, 18 research documents, 14 archive documents, 14 implemented proposals, seven guides, six security-test documents, five architecture documents, two references and one root audit document. These counts describe organisation, not a claim that every historical document received a line-by-line review.

The focused review covered root user/contributor entry points, all seven guides, the design index, the five architecture documents, the current WebUI contract, representative security/integration designs and the API reference. Claims were checked against the current package manifest, security entrypoint, operations catalogue, server, store and ContextCypher bridge. Two independent reviewers checked guides and architecture/design alongside the main review. No application code was changed by this audit.

## Material that is already useful

- [README.md](../../README.md) now describes the security product, standalone and assistant workflows, current capabilities and startup.
- [SECURITY-WORKSPACE.md](../guides/SECURITY-WORKSPACE.md) and [SECURITY-PACKAGING.md](../guides/SECURITY-PACKAGING.md) broadly match the current service, including scoped credentials, optional browser sign-in and deployment limitations.
- [INTEGRATION-TEST-HARNESS.md](previous/docs/guides/INTEGRATION-TEST-HARNESS.md) already introduces the new security tests and labels subsequent harnesses legacy. Its split needs to be more prominent, rather than deleting useful regression coverage.
- [CAPABILITY-AUTHORING-GUIDE.md](previous/docs/guides/CAPABILITY-AUTHORING-GUIDE.md), the architecture overview and forward architecture already contain conversion notices. Keep the useful distinctions while removing conflicting “current” labels below them.
- Historical plans, research and recorded results remain useful when their version and status are explicit. Do not rewrite historical results to make them appear current.

## Recommended cleanup order

1. Fix root installation, usage, security/version policy and contributor instructions first; these actively direct users and coding assistants.
2. Establish a current documentation landing page, service architecture and assistant API reference. Add the GRC workflow guide.
3. Classify remaining design/guidance documents as current, historical or planned. Move historical material only with link updates and clear replacement pointers.
4. Keep the original-byte import gap and GRC identity defect as explicit implementation work. Documentation cleanup alone cannot resolve them.
5. Validate relative links, command existence, version requirements and operator flows against the current package manifest/runtime. Keep production build tests and historical component tests clearly distinguished.

This audit records findings and a cleanup sequence. It does not declare the entire documentation tree current, certify the runtime, or change the published release.
